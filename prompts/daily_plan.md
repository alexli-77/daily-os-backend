从今天的已评分候选中，挑出并改写今天真正要做的 todo。

# 输入

Evidence 里有一个 `todo_scored` 源（`sources.todo_scored.data`）：

- `top`: 已经用程序化评分器排好序的候选数组，每项包含：
  - `rank`: 程序给出的初始排序（1 最高）。
  - `candidateId`: 候选唯一 id（**必须原样回填**，不要改）。
  - `title`: 候选原始标题（可能是 Linear 任务、飞书周要务、vault 笔记或用户随手记）。
  - `source`: 来源（`todo_inbox` / `linear` / `vault` / `weekly_priorities`）。
  - `score` 和 `breakdown`: 总分与加分明细（逾期 / 24h 内到期 / 72h 内到期 / Linear 优先级 / Linear 看板状态 / 日历临近 / carry-over / OKR 关联 / 客户信号）。
  - 可能还有 `dueDate`、`priority`、`stateName`、`stateType`、`okrKrId`、`isCustomerFacing`。

这些分数是**排序建议**，不是命令。你可以微调顺序、合并重复、剔除今天明显不该做的项，但要尊重高分项：`breakdown` 里有 `overdue`、`dueWithin24h` 或高 `okr` 的项，除非有明确理由，否则应进入今日清单。

关于 `stateName`（Linear 看板状态）：

- `In Progress` 表示用户已经动手、还没交付的活。这类候选即使优先级不高、没有 deadline，也应优先考虑——它已经占着用户的注意力，不推进就是烂尾。
- `In Review` 表示已交出去等别人看。除非逾期，否则不要让它挤掉 `In Progress` 的活。
- 今日清单里**至少保留 1 条 `In Progress` 的候选**（`top` 里确实一条都没有时除外）。

关于 `breakdown.restDayDamping`（负分）：今天是用户的休息日，而这条候选来自工作源
（Linear / 每周要务）且既没逾期也不是今天到期，所以被扣了分。它没有被删掉，只是不该
按工作日的密度排。

# 你的任务

0. **用户决策规则优先**：memory 里的 decision-policy（决策规则）是用户亲自写的约束，
   优先级高于本文件的所有默认值。若其中规定了每日任务条数上限（如「最多 3 个重点任务」）、
   信息源优先顺序或排序偏好，严格照办——条数上限与下面的默认区间冲突时，以用户规定为准。
0.5 **作息优先于条数默认值**：prompt 里若有 `# 作息` 一节，它描述今天是工作日还是休息日，
   以及用户自己写的作息表。休息日的工作任务上限以那一节为准，**优先级高于**下面的 5-8 条默认区间；
   `# 作息` 里用户手写的规则又高于系统给的默认句。两者冲突时一律听用户写的那份。
   休息日不是「少排几条工作」，是把位置让给生活、休息、个人项目——`todo_inbox` 和 vault
   来源的候选今天应该占多数。
1. 从 `top` 里选出今天真正要做的条目（默认 **5-8 条**；用户决策规则或 `# 作息` 另有规定时用它们的数字。
   工作和生活可以混排，完全按分数和当天现实排序，不要人为分组）。
2. 把每条候选的 `title` **改写成一句真人助理式的行动指令**，遵守下面的模板规则。
3. 给每条估一个 `minutes`（专注工作的分钟数），规则见下面「耗时估计」。
4. 输出严格的 JSON，不要输出任何解释、Markdown、代码块或额外文字。

# 耗时估计

`minutes` 的用途只有一个：让用户在早上就看出「今天这几条加起来是几个小时」，
从而在开工前砍掉一条，而不是晚上才发现排不下。所以：

- 估的是**净专注时间**，不含开会、通勤、来回切换。
- 粒度取 15 的倍数：15 / 30 / 45 / 60 / 90 / 120。别写 37。
- 范围 5–480 分钟，超出会被服务端截断。
- 一条要是超过 120 分钟，说明它不该是一条今日 todo，优先考虑改写成今天能交付的那一段。
- **宁可不给，也不要瞎给。** 实在判断不出（信息太少、任务边界不清）就省略 `minutes` 字段，
  界面会明说这条没有估时。填一个凑数的数字，会让「今天排不排得下」这个判断彻底失效。

# 改写模板规则（few-shot）

每条 `text`：动词开头、具体到今天能交付的动作、一句话说清做什么，不带证据尾巴、不带「因为」。

- 原始：`LEO-142 todo 评分器` → 改写：`把 todo 评分器的四源归一化写完，跑通去重和排序`
- 原始：`飞书周要务：portfolio 上线` → 改写：`把 portfolio 首页部署到线上，至少能公开访问`
- 原始：`跟进客户 A 合同` → 改写：`给客户 A 发确认邮件，敲定合同签署时间`
- 原始：`健身` → 改写：`下午留 40 分钟做一次力量训练`
- 原始：`vault: 读完 XX 论文` → 改写：`读完 XX 论文并写 3 条要点笔记`

不要写只有短标签的句子（例如「Feishu 旧任务清理」）；要写成能直接照做的一句话。

# 输出格式（严格 JSON）

```
{
  "todos": [
    { "rank": 1, "text": "把 todo 评分器的四源归一化写完，跑通去重和排序", "candidateId": "linear:LEO-142", "minutes": 90 },
    { "rank": 2, "text": "给客户 A 发确认邮件，敲定合同签署时间", "candidateId": "todo_inbox:todo-2026...", "minutes": 15 }
  ],
  "note": "今天逾期项偏多，建议先清逾期再做新任务"
}
```

规则：

- 只输出这个 JSON 对象本身，不要加 ```json 代码块、不要加前后说明。
- `rank` 从 1 开始连续编号，代表你最终认可的今日顺序。
- `candidateId` 必须来自输入的 `top[].candidateId`，原样回填，不要编造。
- `text` 用中文，5-8 条，动词开头。
- `minutes` 是整数，15 的倍数；判断不出来就整个字段省略，不要写 0 或 null。
- `note` 可选：一句话点出今天排序的关键取舍（逾期、客户、OKR 冲突等）；没有可省略或留空字符串。
- 如果 `todo_scored.top` 为空，返回 `{ "todos": [], "note": "今天没有可排的候选，请检查数据源。" }`。
